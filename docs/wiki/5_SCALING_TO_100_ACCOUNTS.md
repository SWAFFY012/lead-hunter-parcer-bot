# Scaling to 100+ Accounts: Architecture of the Future

Текущая монолитная архитектура (Express + одна база SQLite) отлично работает для 5-10 аккаунтов. Однако при масштабировании до 100 активных WhatsApp сессий возникнут "бутылочные горлышки".

## 1. Решение проблемы CPU & Памяти (Multithreading)

Baileys выполняет тяжелую криптографию (AES-GCM шифрование/дешифрование) для каждого сообщения. 100 активных сокетов заблокируют Event Loop в Node.js (так как Node.js однопоточный).

**Архитектура Будущего:**
- **Worker Threads / PM2 Cluster:** Разделение процесса на воркеры. 1 мастер-процесс (управляет REST API) и N воркеров (управляют сессиями Baileys).
- Например, 1 воркер обслуживает 10-15 аккаунтов.
- Общение между воркерами и API должно идти через Redis (Pub/Sub) или встроенные IPC каналы.

## 2. Управление Памятью (Memory Leaks в Baileys)
Baileys по умолчанию хранит в оперативной памяти кеш контактов, сообщений и ключей. 100 аккаунтов приведут к Out-Of-Memory (OOM) крашу.
- **Действие:** Необходимо реализовывать кастомные Store, которые хранят данные не в RAM (объектах JS), а пишут напрямую в Redis или БД, и периодически очищать локальный кеш сообщений.

## 3. База Данных: От SQLite к PostgreSQL
SQLite (даже в режиме WAL) имеет ограничения по конкурентной записи (Concurrent Writes). Когда 100 аккаунтов одновременно будут писать логи, обновлять статус сообщений и лидов, начнутся блокировки (SQLITE_BUSY).
- **Миграция:** Переход на **PostgreSQL** + ORM (Prisma или TypeORM).
- Внедрение пула подключений (Connection Pooling).

## 4. Прокси-инфраструктура
Держать 100 сессий на одном IP — 100% гарантия кластерного бана (Guilt by Association).
- **Интеграция Proxy:** Закупка Mobile IPv4 (с ротацией) или статических IPv4.
- Каждому аккаунту в БД должен быть жестко привязан свой уникальный прокси (`socks5://user:pass@ip:port`).
- `makeWASocket` должен использовать кастомный `agent` для маршрутизации трафика веб-сокета через этот прокси.

## 5. Распределенный Парсинг (Playwright Grid)
1 локальный Playwright не сможет быстро парсить OLX на нужных объемах.
- **Решение:** Использование Selenium Grid или независимых Docker-контейнеров с Playwright. 
- Парсер выносится в отдельный микросервис (Scraping Service), который поставляет данные в главную БД через очередь (RabbitMQ / BullMQ).

## План действий при достижении 15 аккаунтов:
1. Вынести хранение сессий из папки файлов в отдельную таблицу БД или Redis (AuthState).
2. Завернуть Node.js в PM2 cluster mode.
3. Начать внедрение индивидуальных прокси для каждого WhatsApp-номера.
