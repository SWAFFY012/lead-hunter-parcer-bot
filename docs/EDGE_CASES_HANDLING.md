# Edge Cases Handling (Критические Сбои)

Этот документ описывает строгую логику того, как система (Бэкенд) обязана реагировать на критические сбои внешних зависимостей (OLX, Ollama, WhatsApp). Принцип: **Fail Gracefully (Падать безопасно)**.

## 1. Сценарий: Playwright натыкается на Cloudflare Captcha (OLX)

**Ситуация:** Во время парсинга на 3-й странице OLX выдает жесткую капчу, которую бот не может пройти.
**Действие системы (`olxParser.js`):**
1. Отловить исключение `TimeoutError` при поиске элементов объявлений или явное обнаружение селектора капчи (например, `iframe[src*="cloudflare"]`).
2. Сохранить все лиды, успешно спарсенные до этого момента (с 1 и 2 страницы), в БД SQLite.
3. Обновить статус кампании в таблице `campaigns` с `'parsing'` на `'paused'`.
4. Отправить через WebSocket `socket.emit('parser:auth', { message: 'Required Manual Auth' })`.
5. Корректно закрыть контекст браузера (`browser.close()`), чтобы не висели процессы зомби (Chromium).
6. UI должен показать пользователю кнопку "Пройти капчу вручную", которая откроет `headed` браузер.

## 2. Сценарий: Ollama падает посередине батч-генерации

**Ситуация:** Выделено 100 лидов на генерацию AI-сообщений. На 45-м лиде локальная Llama 3 падает из-за нехватки видеопамяти (OOM) или перегрева.
**Действие системы (`ai.js` / API):**
1. Метод генерации должен обрабатывать лиды последовательно (по одному или небольшими чанками) в блоке `try/catch`.
2. Если возникает ошибка `ECONNREFUSED` (Ollama умерла), текущий лид (45-й) и все последующие остаются в БД со статусом `ai_message = NULL` и статусом лида `new`.
3. Все уже сгенерированные лиды (1..44) УЖЕ должны быть сохранены в БД (запись `UPDATE leads SET ai_message = ?` должна идти на каждой итерации, а не в конце массива).
4. Вернуть на фронтенд ответ `206 Partial Content` (или `200 OK` с массивом успешно обработанных и списком ошибок), а также `socket.emit('ai:error', ... )`.

## 3. Сценарий: WhatsApp-аккаунт получает бан (403 Forbidden) во время рассылки

**Ситуация:** Sender Manager использует 3 аккаунта для рассылки кампании на 300 лидов. Во время отправки 10-го сообщения аккаунт "acc_1" ловит бан от Meta.
**Действие системы (`senderManager.js`):**
1. В обработчике сокета `connection.update` ловится `lastDisconnect.error.output.statusCode === 403`.
2. Система МГНОВЕННО обновляет статус аккаунта "acc_1" в БД на `banned`.
3. Функция `sendMessage()` в рассыльщике, которая пыталась отправить сообщение, отлавливает ошибку. Лид возвращается в очередь (или помечается как `failed`).
4. Аккаунт "acc_1" **удаляется из пула активных отправителей** в памяти `senderManager`.
5. Рассылка продолжается с использованием оставшихся двух аккаунтов ("acc_2" и "acc_3").
6. Если забанен последний активный аккаунт в пуле, кампания ставится на паузу (`status = 'paused'`), и на UI вылетает критическое Toast-уведомление.
7. Лог-файл и БД фиксируют время бана для последующего анализа.
