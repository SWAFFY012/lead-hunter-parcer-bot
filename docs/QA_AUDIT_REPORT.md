# Итоговый Отчет QA Аудита (Cross-Check)

## 1. Логические несостыковки и архитектурные дыры
### Критический баг маршрутизации (Express Routing Bug)
В файле `backend/src/routes/leads.js` обнаружена серьезная архитектурная ошибка маршрутизации. Маршруты для экспорта CSV и получения статистики панели управления недоступны:
- Спецификация API (`docs/API_SPECS.md`) описывает эндпоинты `GET /api/leads/export/csv` и `GET /api/leads/stats/dashboard`.
- Однако в коде `backend/src/routes/leads.js` маршрут `router.get('/:id', ...)` определен на строке 37, **до** маршрутов `/export/csv` (строка 91) и `/stats/dashboard` (строка 119).
- **Результат:** При попытке скачать CSV на клиенте (через `window.open('/api/leads/export/csv')`) Express перехватит запрос в роут `/:id`, попытается найти лид с ID "export" и вернет 404 (Not Found).
- **Решение (Fix):** Необходимо переместить объявление маршрутов `router.get('/export/csv', ...)` и `router.get('/stats/dashboard', ...)` выше `router.get('/:id', ...)`.

## 2. Анализ состояния (React State) vs WebSockets
Фронтенд использует базовые хуки `useState` вместе с событиями `Socket.io` (`socket.on`) для реактивности. В целом данные синхронизируются, но есть нюансы:
- Отсутствие глобального стейт-менеджера (Zustand/Redux) приводит к тому, что при открытии нескольких вкладок или переключении между страницами происходят избыточные повторные запросы REST API для обновления данных (например, `leads`, `stats`).
- В компоненте `Leads.tsx` при получении события `lead:replied` фронтенд корректно вызывает перезагрузку данных, если текущий диалог открыт, но при большой нагрузке (множество входящих сообщений) это вызовет лавину REST-запросов (`loadLeads()` и `loadLead()`).
- **Рекомендация:** Реализовать глобальный Store, чтобы точечно обновлять состояние (например, статус или последнее сообщение конкретного лида) прямо из сокет-payload, избегая тяжелых `GET` запросов к БД при каждом чихе.

## 3. Слепые зоны системы и рекомендации

### 1. Блокировки файла базы данных SQLite (SQLITE_BUSY)
Текущая реализация `backend/src/db/database.js` активирует режим `WAL` (Write-Ahead Logging), что является отличным решением. Однако отсутствует параметр таймаута ожидания блокировки. 
При одновременной высокой нагрузке на запись:
- Парсер складывает пачку новых лидов в базу.
- Baileys сокеты одновременно принимают шквал входящих сообщений от прогрева/рассылок и обновляют статусы.
- Массовая генерация AI сообщений через Ollama пишет результаты.
**Следствие:** Приложение упадет с ошибкой `SQLITE_BUSY`.
**Fix:** Добавить `db.pragma('busy_timeout = 5000');` (или больше) сразу после активации WAL в конфигурации базы данных.

### 2. Новые капчи и защиты на OLX (Cloudflare / DataDome)
Парсинг построен на Puppeteer. Если OLX внедрит жесткую проверку (Cloudflare Turnstile), сессия браузера повиснет на бесконечном `await page.waitForSelector(...)`, а процесс на бэкенде зависнет без выдачи ошибки клиенту, или упадет по глобальному таймауту навигации.
**Fix:** 
- Использовать плагины типа `puppeteer-extra-plugin-stealth`.
- Обернуть все шаги парсера в `try/catch` с явным таймаутом и пробросом события `parser:error` через веб-сокеты на фронтенд.
- Для прохождения капчи можно интегрировать API сервисов вроде 2Captcha/Anti-Captcha, если обнаружен селектор окна блокировки.

### 3. Ограничения Ollama и памяти
При массовой генерации (Batch Generation) сообщений на большом количестве лидов Ollama может потребить всю доступную видеопамять (VRAM) / RAM сервера. Отсутствует механизм троттлинга запросов (Concurrency Control) к Ollama API — отправляется сразу массив промисов (предположительно), что вызовет Out of Memory. 
**Fix:** Обрабатывать очередь AI-генерации с конкурентностью = 1 или 2 (через p-limit или async.queue).
